Device grant capacity and rotation review

Projectspeech-therapy
Versionv1
Statusactive · 2026-07-11

Approved locally after redesign: a database slot invariant—not an application count—now caps each learner at five live device grants, while atomic rotation replaces one token without opening a revoke/issue gap.

Context

The preceding milestone made every live grant visible and remotely revocable, but issuance remained unbounded and rotation required a manual revoke followed by issue. The first implementation tried to serialize a count under a learner FOR UPDATE lock. Independent review correctly rejected that design: a PostgreSQL statement can retain a stale MVCC snapshot after waiting for the row lock.

The corrected implementation moves the hard capacity invariant into migration 0023 and keeps replacement delivery one-time. This review covers the migration, issuance retry boundary, rotation/revocation slot lifecycle, all token-consuming gates, API/Server Actions, operator recovery copy, and local verification.

Verdict

Approve the code as a local foundation. Migration 0023 assigns slots 1–5 to existing current grants, aborts if any learner already has more than five, constrains the range, and creates a partial unique index over tenant, learner, and non-null slot. Issuance retries only that named unique-index collision with a fresh statement. Rotation clears and transfers the exact source slot inside the same revoke/insert/audit statement. Follow-up review found no remaining code blocker. Real PostgreSQL/Neon migration and concurrency evidence is unavailable and remains a release gate.
